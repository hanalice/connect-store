# PM 裁决（施工与 QA 验收均以本节为准）

## 裁决①：edit 新消息形态（方案 B 核心规格）

- **不再伪造 toolCall part**（红线：任何 `state:'input-available'` 的人工 part 构造
  均属返工）。edit = 追加一条**用户消息**，格式 = 固定标记 + 人读文本：
  > `[订单修改重发] 请按以下清单重新下单：{标题 × 数量；标题 × 数量…}。请直接调用
placeOrder 工具提交（会再次经过审批），无需向我确认。`
  > （items 按审批卡修改后 draft 渲染，顿号/分号分隔，数量中文数字或阿拉伯数字均可——
  > coder 定，单测锁格式。）
- **消息历史截断不变式（防 MissingToolResultsError 复发）**：新请求的消息列表 =
  当前历史**剔除含未应答审批的 assistant 消息**（`approval.messageId`）+ 追加 edit
  用户消息。验收单测必断言：请求体最后一条 = user 消息含 `[订单修改重发]` 与全部
  修改后条目，且**任何消息不含** `tool-placeOrder` part 或 `tool-approval-request`
  的未应答残留。
- **store 行为**：`approvalSuperseded` 投影语义保留（旧卡显示「已修改并重新发起」）；
  旧 approval 清理（phase 非 pending 化）；machine 事件——`USER_SEND` 从 await_human
  无表内边，走「查表静默跳过 + store 直设 thinking」（sendMessage 既有行为，新预期
  缺口登记报告 §三）；`EDIT` 事件不再发送（edit 不再是机器语义边的行使）。

## 裁决②：prompt 硬约束措辞（防误触发双向往）

`server/chat-prompt.ts` 工具使用节追加一条（server 域本 G 允许改动仅此一处）：

> `- 当用户消息以「订单修改重发」开头并给出明确商品清单与数量时，严格按清单调用
placeOrder 提交（会再次进入审批），不要反问、不要增减数量；普通闲聊中提到商品名
或数字不构成下单意图。`

## 裁决③：mock 剧本与 E2E-AI-21 适配

- mock-bff edit 识别从 toolCallId 启发式（`:362`）改为**用户消息含「订单修改重发」
  标记**分流（既有 `__e2e_order__` 场景的续流函数复用，识别点纯改动 + 断言适配）；
  新卡 `appr-e2e-2` / 订单 `order-e2e0002` 期望输出保持不变。
- E2E-AI-21 断言适配：「新 toolCall → 新卡」表述改为「edit 用户消息 → 模型重新发起
  → 新卡」，断言点（旧卡失效提示 / 新卡内容 / 通过新卡完成闭环）不变；用例数不增。

## 裁决④：design v0.5 补丁 + ADR D11 尾巴（签核后补丁纪律）

- design §6.3 edit 分支描述按 D11 改写（一行级：edit = 新用户回合经官方消息流重发，
  非 toolCall part 绕行；引 D11）；§12 变更记录加补丁行（不升版本号）。
- ADR D11 节尾补「**已实施（G3.3b，2026-10-27）**：edit 重发走新用户回合 + prompt
  硬约束」一句。

## 裁决⑤：基线变动预估与 live 证据纪律
