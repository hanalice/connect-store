# PM 裁决（施工与 QA 验收均以本节为准）

## 裁决①：回合边界接线口径——不改 TRANSITIONS 表的前提下完成接线

G2.2 签核已锁定 `assistantMachine.ts` 的 TRANSITIONS 表不可改。接线中会撞上两个表外问题，
拍板如下：

- **一回合 = 一次 user 消息到 assistant 回复完成（done）**。`done` 是唯一终态、无出边，
  因此 **一回合一机**：`sendMessage` 时若 machine 非空且 `state === 'done'`，新建
  `createAssistantMachine()` 实例开始新回合；首回合直接新建。machine 实例由 store 模块级
  持有（仿 `currentController` 惯例），不进 Zustand state（不可序列化）。
- **error 后用户直接发新消息**：store 先 `send(RETRY)`（error→idle）再 `send(USER_SEND)`
  （idle→thinking），两事件顺序发送、记两条日志。**禁止**为省事私加 `error + USER_SEND` 边。
- **aborted 后发新消息**：`aborted + USER_SEND → thinking` 是合法边（#20），直接发送。
- **收尾事件纪律**：流收尾（`STREAM_END` / `ERROR` / `TOOL_*`）发送前必须过 A4 代际校验
  （存量逻辑保留）；且须先查表预判 `TRANSITIONS[state][event]` 存在再 send——abort 后旧流
  收尾不得依赖 machine 的 warn 拒绝做控制流（预期内 warn 噪音 = 实现缺陷）。abort 后
  machine 终态必须是 `aborted`，不得被任何后续事件顶掉。
- `reset()` = 中止当前流 + 丢弃 machine 实例，回到全新 idle。

## 裁决②：AssistantStatus 5 态 → AssistantState 9 态统一方案

- 删除 `types/assistant.ts` 的 `AssistantStatus`（G2.2 已改其注释指向 machine 为事实源，
  本 G 完成统一）；全仓引用点（`useAssistantStore.ts` 及其测试等）改为从
  `assistantMachine.ts` 导入 `AssistantState`。
- store 的 `status` 字段类型 = `AssistantState`，每次 machine 事件后同步；UI 的 isBusy 口径
  扩为 **thinking | streaming | tool_calling | tool_result** 四态（停止按钮在这四态可用，
  对应 USER_ABORT 四条边）。
- `await_human` 在 G2.3 不可达（三工具全部自动执行、placeOrder 不存在），但其类型与映射
  本 G 一并定义（badge 静态映射 9 态），交互验证留 G3.3。

## 裁决③：AgentStatusBadge 同 G 落地（范围判断依据）

- todo 完成标准「状态投影正确」需要一个 9 态消费点；store 接线后 ChatPanel 存量 status 判断
  必须重写，badge 是 design §7 指定的最小消费点，不同 G 拆分只会留下半成品 ChatPanel。
- `docs/regression-index.md` 已将 INT-AI-05（AgentStatusBadge 投影）归入 G2.3，拆分将造成
  索引归属动荡。
- 依据以上三点，**ToolCallPanel 与 AgentStatusBadge 同 G 交付**；但 badge 只做静态投影
  （状态 → 文案/视觉/ARIA），不做 await_human 交互（G3.3）。

## 裁决④：tool-output 展示深度

- `ToolCallPanel` 展示四要素：**工具名 / 参数（格式化 JSON）/ 状态（执行中·成功·失败）/
  耗时（ms）**；结果仅展示摘要（截断 JSON 文本或成功/失败标记），**不做商品卡 / 网格 / 空态
  组件**——那是 G2.4 uiRegistry 的范围。

## 2. useAssistantStore 接线 assistantMachine

- chunk → machine 事件映射（全部复用 `onChunk` 透传，协议不自造——ADR D8）：

  | 时机                                | machine 事件 | detail                                     |
  | ----------------------------------- | ------------ | ------------------------------------------ |
  | sendMessage 起始（合法前提见裁决①） | USER_SEND    | —                                          |
  | chunk `tool-input-available`        | TOOL_CALL    | `{tool: toolName, args: input}`            |
  | chunk `tool-output-available`       | TOOL_RESULT  | `{result: output, durationMs: 实测耗时}`   |
  | chunk `tool-output-error`           | ERROR        | `{result: error}`（tool_calling→error 边） |
  | chunk `text-start`（最终回复首帧）  | STREAM_START | —                                          |
  | 流正常结束                          | STREAM_END   | —                                          |
  | error chunk / `ChatApiError`        | ERROR        | —                                          |
  | `abort()`（isBusy 四态内）          | USER_ABORT   | —                                          |

- chunk 类型字段以 `ai@7` 的 `uiMessageChunkSchema` 实际定义为准（toolCallId / toolName /
  input / output / error），施工前先核对安装版本类型。
- `ChatMessage` 扩展 `toolCalls?: ToolCallInfo[]`（`types/assistant.ts` 本 G 允许扩展）：
  `{toolCallId, toolName, input, output?, error?, startedAt, endedAt?}`；`durationMs =
endedAt - startedAt`（`performance.now()`）。渲染数据源 = 消息上的 toolCalls（不读
  machine log）。
- A4 代际防护逻辑保留不动；收尾事件遵守裁决①的查表预判纪律。
