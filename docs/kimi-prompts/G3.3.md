# 目标

交付审批前端切片 + **端到端闭环**（Showcase 最终前端切片）：

- **ApprovalCard 整体替换**（G2.4 静态占位 → 真审批卡）：订单摘要（条目 / 数量 / 金额 /
  orderId / TTL 倒计时）+ 三按钮 approve / reject / edit + 取消订单；
- **`addToolApprovalResponse` 协议接线**（自研传输层等价实现：approval-request chunk →
  卡 → 决策 → 消息历史回放复放）；
- **`await_human` 状态投影首次可达**（badge 占位映射激活 + machine 事件接线）；
- **端到端闭环**：对话 → 推荐 → 加购 → 下单 → 审批 → 订单号；reject 后 AI 修正链路；
  edit 走「不发审批、带修改重新发起」。

完成标准（todo G3.3 行）：浏览器完整闭环；reject 后 AI 修正链路跑通；edit 重新发起。
编号映射：INT-HITL-01（approve）/ 02（reject+reason）/ 03（edit）/ 04（TTL 过期卡态）。

# PM 裁决（施工与 QA 验收均以本节为准）

## 裁决①：prompt 能力声明——server 域本 G 唯一允许改动（A 裁决落地）

- **允许改动 = `server/chat-prompt.ts` 能力声明一节，仅此一处**；其余 server 文件
  （chat.ts / approvals.ts / orders.ts / tools/ / env.ts / index.ts）**零改动**
  （越界即返工）。
- **PM 给定替换文案**：删除「- 你没有下单、支付或审批能力，不要提及此类能力；交易动作
  引导用户自行完成。」，替换为：
  > `- placeOrder：提交订单（不可逆）。当用户明确要求下单 / 结算时，调用 placeOrder
工具；工具会生成订单审批请求，你在用户通过界面确认之前不会得到执行结果——确认
期间向用户说明「正在等待确认」，绝不暗示交易已完成。所有订单都必须经过用户确认，
不存在免审批路径。用户拒绝时，根据反馈（如「太贵了」）推荐更合适的商品。`
- **不写金额阈值**（G3.2 策略 = placeOrder 恒审批，阈值仅为机制演示——prompt 提阈值
  会与策略不符，属编造）。

## 裁决②：ApprovalCard 整体替换——删旧建新 + INT-HITL 编号映射

- **删旧建新**：删除 G2.4 静态占位实现与其单测，重写 `ApprovalCard.tsx`（+
  module.scss + test）。新卡 props 驱动（纯展示 + 回调）：订单摘要（items 行：标题 /
  数量 / 小计；合计；orderId；**TTL 倒计时** = expiresAt − now，卡内 1s 级刷新，
  coder 定手法）+ 四操作：✓ 确认下单 / ✗ 拒绝（带 reason 输入或预设选项，coder 定
  最小形态）/ ✎ 修改 / 取消订单。
- **编号映射声明**：INT-HITL-01 = approve 点击（回调 fired + 卡转执行中态）；
  INT-HITL-02 = reject + reason（回调携带 reason）；INT-HITL-03 = edit 步进/移除 +
  重新发起；INT-HITL-04 = 倒计时归零 → 按钮禁用 + 「已过期，请重新发起」提示。
  标题嵌编号进单测。

## 裁决③：edit 语义最小形态——卡内改数量 / 移除条目，确认后新 toolCall 重发

- edit **不换商品**（换商品 = reject 后对话改需求）；最小形态 = 卡内数量步进（±）与
  条目移除，改后合计实时重算（前端按 store 现价算展示值，最终以 server 实时计价为
  准，G3.2 裁决①），「确认修改并重新发起」→ **不发审批响应**。
- 重发形态：新 `/api/chat` 请求，消息历史 = 原历史 + assistant 消息含**新 tool-call
  part**（toolName: placeOrder，新 toolCallId，input = 修改后 items）——part 具体形态
  **以 ai@7 类型核对为准**（裁决④纪律）；后端收到新 toolCall → 旧单自动 rejected +
  新单 pending（G3.2 已实现，前端只负责构造）。
- machine 事件：点「确认修改」发 **EDIT**（`await_human + EDIT → tool_calling`，
  `:99` 合法边）。

## 裁决④：addToolApprovalResponse 协议接线——自研层等价实现 + 类型核对纪律

- **approval-request → 卡**：`tool-approval-request` chunk 经 chatApi 校验透传（须先核
  `uiMessageChunkSchema` 是否覆盖该类型；不覆盖 = 报备不一致项，最小扩展须过 schema
  不自造）；store 在 onChunk 收到后发 **APPROVAL_REQUEST**（`streaming → await_human`
  合法边 :91），并把请求数据（id / 关联 toolCallId / input / expiresAt 等，**以 ai@7
  帧字段为准**）落状态供卡渲染。
- **三按钮 → 回放**：approve = 新 chat 请求，历史 = 原历史 + assistant 消息含
  **tool-approval-response part**（`{ id, approved: true }`；part 形态以 ai@7 类型为准）；
  reject = 同构造 `approved: false`——**reason 反馈形态以类型核对为准**：part 支持
  reason/detail 则携带「太贵了」类文本，不支持则在该 part 后追加 user 文本消息
  （兜底拍板，coder 报告核对结论）。
- **reject 修正链路形态**：denied 复放 → 模型收到 `execution-denied` → 续跑生成修正
  方案（替代商品出现在后续回复文本，E2E/单测断言此语义）；链路不新开回合。
- 所有审批回放请求 **过 A4 代际校验 + 查表预判**（既有纪律，G2.3 裁决①）；chunk /
  part 字段一律以安装的 `ai` 包类型定义核对（G3.1 §六 措辞纪律：「从已登记 toolCall
  取 toolName」）。

## 裁决⑤：await_human 投影与取消——首次可达的验收口径

- badge 占位映射（AgentStatusBadge :18「等待确认」）本 G 首次真实可达：验收 =
  E2E 断言 APPROVAL_REQUEST 后 badge 文案变为「等待确认」、决策后离开。
- **取消订单**：审批卡「取消订单」→ store 增量允许 await_human 取消（现 abort 判
  isBusy 四态会拒——`useAssistantStore.abort` **只增不改**地纳入 await_human：
  `await_human + USER_ABORT → aborted` 是表内合法边 :100）；停驻 aborted、不执行订单。

## 裁决⑥：表缺口纪律 + E2E 编号 + live 走查

- **表缺口预期出现**（如 `streaming + TOOL_CALL`、`tool_calling + APPROVAL_REQUEST`
  等组合）：走「查表静默跳过 + store 兜底」既有机制（G2.3 §三①），缺口登记报告 §三，
  **不得私改 TRANSITIONS**；UI 投影真值 = store status（既有模式）。
- **E2E 拍板**：新增 **E2E-AI-19~21**（mock 门禁 17 → 20）：
  - **E2E-AI-19** 审批通过闭环：`__e2e_order__` 场景（首请求 → text + tool-approval-request
    → 停驻；带 approval-response 的第二请求 → 订单号 + 回复完成；badge await_human 投影
    序列断言；映射 INT-HITL-01）；
  - **E2E-AI-20** reject 修正：denied 复放 → 修正文本出现（INT-HITL-02）；
  - **E2E-AI-21** edit 重新发起：卡内改数量 → 新 toolCall → 新审批卡（旧卡失效提示，
    INT-HITL-03）。
    mock-bff 加**有状态场景**（第二请求检测 approval-response / 新 toolCall 分流），
    不改既有场景。
- **live 走查**（H2 前置）：真 BFF（配 `APPROVAL_SECRET`）+ 真模型走
  「推荐 → 加购 → 下单 → 审批 → 订单号」全链；LLM 不确定性应对 = 失败**重试 ≤1 次**
  并记录两次 transcript；live 不进默认门禁。
- 单测基线 94 → **≥104**（+10：ApprovalCard 4 / 接线与投影 3 / chatApi 回放构造 2 /
  取消路径 1，分布 coder 可调）。
