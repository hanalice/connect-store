### 6.5 prompt 冲突裁决（工单级，PM 拍板）——选 A：并入 G3.3 工单

**裁决：A**（不立 G3.2b；在 G3.3 工单「要做的事」显式列入 prompt 能力声明更新，
并给定 PM 替换文案）。理由：

1. **耦合性**：prompt 声明与 G3.3 端到端闭环强耦合——不改声明，live LLM 永不触发
   placeOrder，G3.3 浏览器闭环无法 live 实测；G3.3 验收天然覆盖该声明的正确性
   （改错声明 = 闭环不通 = G3.3 验收失败）。
2. **G3.2 完整性不受影响**：本 G 验收口径全部在 curl / mock 集成层，后端 HITL 安全链
   已独立闭合；prompt 是引导模型行为的文案层，不是安全层（安全由 toolApproval +
   签名 + 状态守卫保证，无 prompt 也零绕过面）。
3. **成本**：G3.2b 会产生「1-2 行改动 + 无独立测试面 + 仍待 G3.3 才能验证」的碎片
   工单，MAF 循环成本高于收益。
4. **边界防护**：G3.3 工单将显式写「server 域允许改动**仅限** `chat-prompt.ts` 能力
   声明一节（PM 给定文案，越界即返工）」——跨域不被滥用。

**PM 给定替换文案方向**（G3.3 工单落全文）：删除「你没有下单、支付或审批能力」，
改为「当用户明确要求下单 / 结算时，调用 `placeOrder` 工具提交订单；该工具会生成
订单审批请求，**必须等待用户在界面中确认后才会执行**；审批期间向用户说明正在等待
确认，不要声称交易已完成」。
