  为 **streamText 顶层调用选项**（ai@7.0.148 `index.d.ts:3803` 顶层解构），非 settings 子对象；
  集成测试补充 ai@7 行为细节：user-approval 的 request part 无 `isAutomatic` 字段；
  复放时策略回调被 SDK 重估（policyDecisions 双段序列）。

  `parseToolsDirectAllow` 交集之后再剔除，注释级约束升级为可测断言（vitest + curl 双实证）。
- 订单四态 + 惰性过期 + 审计链模型可作为 G3.3 前端 ApprovalCard 的状态数据源契约。

## 五、风险与遗留

- **prompt 冲突（升级 PM，§三已记）**：`chat-prompt.ts:23` 告知模型「没有下单能力」，
  placeOrder 在 live 下永远不会被模型触发，G3.2 后端 HITL 全链只在 mock 集成测试与 curl
  层实证。G3.3 接线 ApprovalCard 前须先解决 prompt 口径（PM 裁决：改 prompt 或单独工单）。
- **edit 语义全局化（声明点⑤-3，QA 接受偏离但列观察）**：工单裁决⑥ 措辞为
  「旧 order 标记 rejected」（单数），实现为 `listPendingOrders()` 全量 reject
  （`approvals.ts:99-105`）。单用户 Showcase 下等价（同时刻至多一张 pending 单），
  但多会话共用内存单例时，A 用户新单会拒掉 B 用户 pending 单——属跨会话干扰隐患，
  建议 G3.3 或后续按 cart/会话维度收敛。
- **环境遗留**：coder 验收进程（8791）曾被遗留在后台，QA 已清理；建议后续验收
  「用完杀」写进检查单。
- live-LLM 下单链路零实证（与 prompt 冲突同根因）；API-AI-01/04/05/06 编号行已登记
  `docs/regression-index.md` §2.3（⬜→✅）与 `docs/test_cases.md` §5.2（落地登记）。
