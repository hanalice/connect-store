## 3. 总体方案：单 G 三段式循环

每个 G 任务走同一循环（主会话 = 编排器，三个角色各为独立上下文子代理）：

```
施工工单（docs/kimi-prompts/Gx.y.md，沿用现有模式）
   │
   ▼
coder 子代理：按工单施工 → 自测三件套 → 提交 feat/fix
   │
   ▼
QA 子代理（独立上下文，未见施工过程）：
   按 test_cases.md + 工单验收标准执行机器可判项 + Playwright E2E
   → 写 docs/reports/Gx.y.md 的「QA 测试报告」与「问题与解决」节（逐条 ✅/❌ + 证据输出）
   │  ❌ → 打回 coder（inter_agent_chat.md 记录，最多 N=2 轮，超过转人工仲裁 H4）
   ▼
PM 子代理（独立上下文）：
   对照 design v0.4 / todo 完成标准 / DoD 四条逐项签核
   → 补全 docs/reports/Gx.y.md 的「PM 验收签核」节
   → 通过则回写 todo.md 状态列 + 推进 maf_manifest.json + 提交 docs 簿记
```

**manifest 阶段映射**（保留 maf 骨架语义，不发明新阶段名）：

## 4. 编排器与工单生命周期（v0.3 新增）

### 4.1 编排器 = 主会话（无状态，文件即现场）

- **触发模型 B（试点采用）**：用户一句「推进 maf」→ 主会话读 `maf_manifest.json` 定位下一个 G
  → 依次派 coder/QA/PM 子代理 → 收口 → 停在闸门处。用户介入点 = 触发 + 闸门。
- **不选 cron 定时自启**：会话不在线则不触发，且 H2/H4/H6 闸门本就要求用户在场，
  定时自走只会撞在闸门上。
- **角色实现方式**：coder/QA/PM = 主会话发起的**一次性子代理调用**（干完即销毁，
  结论以文件和返回值落地），不是常驻 tmux 进程——这是对 maf 原始「角色 = 常驻 tmux 会话」
  模型的有意退化；tmux 只用于跑 dev server / Playwright webServer。
- **主会话无状态**：现场 = manifest（到哪了）+ `docs/reports/`（各 G 结论）+
  `inter_agent_chat.md`（交接轨迹）。编排器可随时死、随时换会话，状态不丢。

### 4.2 单 G 编排循环（9 步）

| 步         | 执行者       | 动作                                                                             | 文件变化                    |
| ---------- | ------------ | -------------------------------------------------------------------------------- | --------------------------- |
| ① 触发     | 用户         | 「推进 maf」（试点期每 G 一次）                                                  | —                           |
| ② 定位     | 主会话       | 读 manifest 找下一个 pending；读 todo.md 确认 depends_on 已 done                 | —                           |
| ③ 工单就绪 | 主会话       | 工单存在且 `prompt_status: ready`？否则转工单生产线（§4.3）                      | 工单 draft → ready          |
| ④ 派 coder | coder 子代理 | prompt = 工单全文；施工 → 三件套自测 → commit                                    | 代码 + feat 提交            |
| ⑤ 廉价门禁 | 主会话       | 快查 git log 有提交、npm test 绿（不烧 QA 上下文走红状态）                       | —                           |
| ⑥ 派 QA    | QA 子代理    | 独立上下文跑验收 → 写报告第一~五节                                               | `docs/reports/Gx.y.md`      |
| ⑦ 打回分支 | 主会话       | fail → inter_agent_chat 记 @coder → 回 ④（上限 2 轮）；第 3 次 → H4              | inter_agent_chat.md         |
| ⑧ 派 PM    | PM 子代理    | 读报告全文 + design + DoD → 写报告第六节签核                                     | 报告第六节                  |
| ⑨ 收口     | 主会话       | 回写 todo.md → 推进 manifest → chat 记录 → commit 簿记 → PM 起草下一 G 工单 → 停 | todo / manifest / docs 提交 |

### 4.3 工单生产线：谁写、何时写

- **谁写**：PM 角色。工单 = design/todo 翻译成施工指令，是 PM 的任务分解职责；
  coder 不自出题（自出题 + 自答题 + 自评分 = 三重利益冲突）。
- **何时写**：
  - 试点期（G1.4）：主会话起草 → **用户逐字过目** → 标 `ready`；
  - 推广期（G2 起）：上一 G 收口时（第 ⑨ 步）PM 子代理起草下一个，标 `draft`，
    用户在 Phase 边界抽验（H6）批量审，触发前随时可改。
- **不全部预写的原因**：工单质量依赖上一 G 产出——报告的「问题与解决」「风险与遗留」节
  和 `shared-assets.md` 新条目都是下一个工单的关键输入；全部预写等于放弃这个信息。
- **PM 写工单的必读输入**：todo.md 任务详情行 → design 相关章节 → `test_cases.md` 用例编号 →
  上一 G 报告（尤其第三、五节）→ `docs/ai-assistant-shared-assets.md`。
- **工单结构**：沿用 G1.3 已验证的解剖：frontmatter（`todo_id` / `design_version` /
  `depends_on` / `prompt_status`）+ 目标 + 前置读取 + 现状 + 要做的事 + 明确不做 +
  验收标准 + 提交规范 + 数据报告要求 + 完成后输出。

### 4.4 工单读者矩阵

| 读者         | 时机                       | 读什么                              | 不读什么                           |
| ------------ | -------------------------- | ----------------------------------- | ---------------------------------- |
| 主会话       | 循环 ②③                    | 只看 frontmatter + 验收节标题       | 不读全文（省上下文）               |
| coder 子代理 | 被 spawn 时（prompt=全文） | 全部，尤其「明确不做」              | 不读 QA/PM 模板                    |
| QA 子代理    | coder 提交后               | 验收节 + 提交规范 + `test_cases.md` | 不读 coder 工作过程/自述（独立性） |
| PM 子代理    | QA pass 后                 | 完成标准 + design 章节 + 报告全文   | 不读 coder 会话                    |
| 用户         | 闸门处                     | 报告 + 想抽验的任意层               | —                                  |

### 4.5 工单状态机与中断恢复

- **`prompt_status` 状态机**：`draft`（PM 起草完待审）→ `ready`（可施工）→ `doing`
  （coder 已领，防重复派发）→ `done`（PM 签核）。工单级锁与 manifest `g_tasks`
  由编排器在第 ④⑨ 步同步。
- **中断恢复**（任何一步崩溃后，新会话被触发时）：读 manifest → 找 `doing` 态 G →
  看 `docs/reports/Gx.y.md` 存在性与各节完整度 → 有一~五节 = QA 完成待 PM；
  无报告则看 git log 有无未签核 feat 提交 = coder 完成待 QA；都没有 = 重派 coder。
  不依赖任何会话记忆。

## 5. 阶段报告与通用资产沉淀

### 5.1 每 G 一份阶段报告：`docs/reports/Gx.y.md`

定位 = **阶段性 present**（可对外讲的交付陈述），QA 与 PM 双报告合一文件、分节署名。
固定六段结构（模板见 `docs/reports/_template.md`）：

| 节               | 内容                                                     | 执笔  |
| ---------------- | -------------------------------------------------------- | ----- |
| 一、本阶段交付   | 做了什么：变更清单、commit 号、关键数据（如 chunk 粒度） | QA    |
| 二、QA 测试报告  | 逐条验收标准 ✅/❌ + 命令与输出证据（不贴结论贴证据）    | QA    |
| 三、问题与解决   | 碰到的问题：现象 / 根因 / 解法（含打回记录）             | QA    |
| 四、通用资产沉淀 | 本阶段沉淀的可复用资产摘要 → 详情写入 §5.2 的单独文档    | QA    |
| 五、风险与遗留   | 需要关注的风险、遗留问题、后续任务的预警                 | QA+PM |
| 六、PM 验收签核  | DoD 四条 + design 一致性 + todo 完成标准逐项核对结论     | PM    |

**为什么放 `docs/reports/` 而不是 `.agents/maf/`**：`.agents/` 在 `.gitignore` 里
（agent-hub 本机物化视图，不提交）。报告是交付物、要进版本库接受审阅；
`.agents/maf/` 只留运行时数据（manifest / inter_agent_chat / monitor）。

### 5.2 通用资产单独文档：`docs/ai-assistant-shared-assets.md`

跨 G 复用的工程资产登记处，每个 G 的「通用资产沉淀」节只写摘要，详情追加到本文档。
资产条目格式：**名称 / 来源任务 / 解决什么问题 / 复用方式 / 代码位置**。
示例（G1.3 已沉淀的首批条目）：自研传输层错误三分类模式（network/http/stream）、
SSE 受控流单测构造法、智能滚动阈值模式、Zustand 模块级 AbortController 竞态防护。

### 5.3 与面试叙事的关系

阶段报告的「问题与解决」「通用资产沉淀」两节直接对应面试追问
（"遇到过什么坑" / "有什么可复用的设计"），写报告 = 顺手攒话术素材。

## 6. 验收机制修改点（决策①已同意）

**现状**：coder 自测 + **用户人工验收**（G1.3 模式：agent 报告数据，用户确认后才回写状态）。

**已批准的新机制**：

| 验收类别                                                                | 现状承担者 | 新承担者                        |
| ----------------------------------------------------------------------- | ---------- | ------------------------------- |
| 机器可判项（npm test 数字 / curl / lint / build / Zod 报错 / 签名拦截） | coder 自测 | **QA 子代理独立执行**，输出证据 |
| 浏览器行为项（流式渲染 / 停止 / 折叠 / 滚动 / 错误态 / 审批闭环）       | 用户人眼   | **Playwright E2E**（mock 流）   |
| 合规签核（DoD 四条 / design 一致性 / todo 完成标准）                    | 用户       | **PM 子代理**逐项核对           |
| 面试叙事质量 / demo 观感 / 最终放行                                     | 用户       | **保留用户**（见 §7 闸门）      |

**治理变更声明**：人工验收从「每个 G 一次」降级为「Phase 边界抽验 + 最终 demo」——
**用户已于 2026-10-22 同意**。

## 9. Playwright 方案（决策②③已同意）

- **引入**：`@playwright/test`（devDependency）+ `playwright.config.ts` + `e2e/` 目录；
  不触碰 `vite.config.ts` 与 `server/` 现有逻辑。
- **确定性策略（决策③，已同意）**：E2E 默认用 `page.route('/api/chat')` 拦截，
  回放手写/录制的 UIMessageChunk SSE 流——确定、快速、零 API 成本，可精确构造断流/错误帧等
  边缘场景；对齐 design §9「LLM 是不确定依赖，测试必须确定性」。
  另保留 1–2 条 live 冒烟（真打 BFF + DeepSeek）防「BFF 流格式漂移而 mock 过期」，
  因慢 / 费 / 偶发失败而**不进 CI 门禁**，本地发布前手动跑。
  兜底说明：真实流格式另有 QA 每 G 的 curl 验收覆盖（如 G2.1）。
- **覆盖用例**（随 G 任务增量补充，非一次性写全）：
  对话页加载 / 逐块增量渲染（DOM 分帧断言）/ 停止→aborted / reasoning 默认折叠 /
  智能滚动（上滑不抢、回底跟随）/ 错误态横幅（route abort 模拟断网）/ G3 审批闭环主路径。
- **webServer 配置**：Playwright 自动起 `vite dev`；mock 拦截模式下 BFF 无需启动。
- **CI**：G4.1 时接入 GitHub Actions（mock 模式 E2E 进门禁；live 冒烟不进）。

## 11. 风险与成本

| 风险/成本                        | 量级         | 缓解                                                             |
