# MAF 半自动化交付方案（AI 导购 G1.4 – G4.4）

> 版本：v0.1（2026-10-22，待用户拍板）
> 定位：用 maf（multi-agent-flow）工作流承接 `docs/ai-assistant-todo.md` 剩余任务的执行与验收，
> 跳过 Requirements / Architecture / Security 阶段（设计已定稿），只做「施工 → 验收 → 签核」循环。
> 本文档是**提案**，批准后才初始化 `.agents/maf/`；未批准前不动现有代码与治理。

---

## 1. 目标与范围

- **目标**：剩余 G 任务（G1.4、G2.1–G2.4、G3.1–G3.4、G4.1–G4.4）由 maf 角色分工半自动完成；
  QA 角色负责机器可判验收 + Playwright 浏览器验收，PM 角色负责对照 design / DoD 签核。
- **范围外（明确不做）**：不并行施工（依赖链为纯串行）；不改 design v0.4 已拍板的技术决策；
  不自动触碰 `~/hermes-agent` 与 `~/wiki`（硬约束第 8 条）。

## 3. 总体方案：单 G 三段式循环

每个 G 任务走同一循环（主会话 = 编排器，三个角色各为独立上下文子代理）：

```
施工工单（docs/kimi-prompts/Gx.y.md，沿用现有模式）
   │
   ▼
coder 子代理：按工单施工 → 自测三件套 → 提交 feat/fix
   │
   ▼
QA 子代理（独立上下文，未见施工过程）：
   按 test_cases.md + 工单验收标准执行机器可判项 + Playwright E2E
   → 落 .agents/maf/qa_report.md（逐条 ✅/❌ + 证据输出）
   │  ❌ → 打回 coder（inter_agent_chat.md 记录，最多 N=2 轮，超过转人工仲裁）
   ▼
PM 子代理（独立上下文）：
   对照 design v0.4 / todo 完成标准 / DoD 四条逐项签核
   → 通过则回写 todo.md 状态列 + 推进 maf_manifest.json + 提交 docs 簿记
```

**manifest 阶段映射**（保留 maf 骨架语义，不发明新阶段名）：

| maf Phase      | 映射                                           | 进入状态         |
| -------------- | ---------------------------------------------- | ---------------- |
| Requirements   | 已有产物：design §1–§2 / 硬约束                | 直接标 completed |
| Architecture   | 已有产物：design 全文 + ADR D1–D10             | 直接标 completed |
| Security       | 已有产物：硬约束 / ADR D9 / design §8 安全节   | 直接标 completed |

| Operations     | G4.2–G4.4（README / 文档 / 验收收口）          | pending          |

## 4. 验收机制修改点（需用户拍板）

**现状**：coder 自测 + **用户人工验收**（G1.3 模式：agent 报告数据，用户确认后才回写状态）。

**提议**：

| 验收类别                                                                | 现状承担者 | 提议承担者                           |
| ----------------------------------------------------------------------- | ---------- | ------------------------------------ |
| 机器可判项（npm test 数字 / curl / lint / build / Zod 报错 / 签名拦截） | coder 自测 | **QA 子代理独立执行**，输出证据      |
| 浏览器行为项（流式渲染 / 停止 / 折叠 / 滚动 / 错误态 / 审批闭环）       | 用户人眼   | **Playwright E2E**（确定性 mock 流） |
| 合规签核（DoD 四条 / design 一致性 / todo 完成标准）                    | 用户       | **PM 子代理**逐项核对                |
| 面试叙事质量 / demo 观感 / 最终放行                                     | 用户       | **保留用户**（不可委托，见 §5）      |

**治理变更声明**：人工验收从「每个 G 一次」降级为「Phase 边界抽验 + 最终 demo」。
这是本方案最大的治理修改点，需用户明确同意；不同意则退回每 G 人工验收，maf 只做施工与 QA 分流。

## 7. Playwright 方案

- **引入**：`@playwright/test`（devDependency）+ `playwright.config.ts` + `e2e/` 目录；
  不触碰 `vite.config.ts` 与 `server/` 现有逻辑。
- **确定性策略（关键决策）**：E2E **默认用 `page.route('/api/chat')` 拦截**，回放手写/录制的
  UIMessageChunk SSE 流（含 reasoning-delta / tool-\* / approval 部件）——确定、快速、零 API 成本，
  对齐 design §9「LLM 是不确定依赖，测试必须确定性」。
  另保留 1–2 条 live 冒烟（真打 BFF + DeepSeek），标记为非 CI 门禁、本地手动跑。
- **覆盖用例**（随 G 任务增量补充，非一次性写全）：
  对话页加载 / 逐块增量渲染（DOM 快照分帧断言）/ 停止→aborted / reasoning 默认折叠 /
  智能滚动（上滑不抢、回底跟随）/ 错误态横幅（route abort 模拟断网）/ G3 审批闭环主路径。
- **webServer 配置**：Playwright 自动起 `vite dev`；BFF 在 mock 拦截模式下无需启动（live 冒烟才需要）。
- **CI**：G4.1 时接入 GitHub Actions（mock 模式 E2E 进门禁；live 冒烟不进）。

## 9. 风险与成本

| 风险/成本                        | 量级                                   | 缓解                                                 |
| -------------------------------- | -------------------------------------- | ---------------------------------------------------- |
| 上下文开销                       | 每 G 约 3 份（coder/QA/PM 独立上下文） | 工单自带前置读取清单，压缩上下文                     |
| maf 初始化 + 工单模板 + 编排纪律 | 0.5–1 天                               | 从 G1.4 试点一个循环后再推广                         |
| QA 子代理误判/漏判               | 中                                     | 验收只认命令输出证据；H6 人工抽验兜底                |
| Playwright flake                 | 中                                     | mock 流确定性 + 重试 1 次；live 冒烟不进 CI          |
| 真实 LLM 抖动影响验收            | 中                                     | E2E 不依赖真模型；curl 类验收允许 QA 重试 1 次并记录 |
| 子代理死循环（打回—重修）        | 低                                     | 2 轮上限 → H4 人工仲裁                               |
| 回退成本                         | 低                                     | 任意时刻退回单会话工单模式（G1.1–G1.3 已验证）       |

## 10. 决策点（批准前需逐项拍板）

1. **治理变更**：人工验收降级为 Phase 边界抽验 + 最终 demo，每 G 由 PM 子代理签核回写——同意？
2. **Playwright 转正**：引入 devDependency + `e2e/`（design §9 原为可选）——同意？
3. **E2E 确定性策略**：默认 route 拦截 mock 流，live 冒烟不进 CI——同意？
4. **人工闸门清单**（§5 的 H1–H6）——有增删？
5. **试点范围**：先只跑 G1.4 一个完整循环复盘后再推广，还是直接全量铺开？

## 11. 批准后的实施顺序

1. `init-maf.sh` 初始化 `.agents/maf/`，按 §3 预填 manifest（前 3 phase 标 completed）。
2. 写 QA / PM 工单模板 + G1.4 施工工单。
3. 引入 Playwright 基建（最小：配置 + 1 条对话页加载用例）。
4. 跑 G1.4 完整三段式试点 → 复盘（工时 / 误判 / 闸门有效性）→ 修订本方案。
5. 按依赖链推进 G2.1 → G4.4，每个 Phase 边界触发 H6 抽验。
